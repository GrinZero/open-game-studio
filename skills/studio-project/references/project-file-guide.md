# 游戏项目文件规范

版本：1.2 · 2026-10-13 · Open Game Studio 可选规范

这套规范帮助独立开发者为文件建立稳定的名字、位置和依赖边界，也适用于小团队。它吸收 Allar / Gamemakin 与 bakneko 的指南，将引擎特定做法拆成通用规则和引擎适配。完整规则供制作时查阅，快速入门用于确定第一步；二者使用同一套约定。

用户可以全部采用、按章采用或继续使用已有规则。安装插件、登记项目、阅读本文都不会自动启用规范。当前提供文档和 Codex 对话指导，没有界面开关、自动文件检查器或迁移器。

文件规则、引擎适配和版本控制方式分别选择。规范不要求用户安装 Git；Diversion、Perforce、Unity Version Control、Git 或明确的可恢复快照均可按实际项目采用，也可让代码与美术使用不同后端。

## 0. 快速入门与查阅入口

第一次采用可以说：

> 在我指定的游戏项目中采用 Open Game Studio 文件规范的标准方案。识别现有引擎和目录，只建立当前需要的部分，把采用范围和例外写入 PROJECT_STRUCTURE.md，保留旧文件原位。

也可以说“只采用命名章节”或“根据规范检查现有项目并给建议”。讨论、检查和采用都不等于授权批量移动旧资源。

| 当前问题                                          | 阅读位置                                 |
| ------------------------------------------------- | ---------------------------------------- |
| 项目从哪里开始、文件放哪里、哪些可以共享          | 本文第 1–5 章                            |
| 模型、贴图、动画、UI、音频等具体怎么命名          | [命名与资源类型速查](asset-naming.md)    |
| Godot、Unity、Unreal 怎样落实；模型和贴图怎样验收 | [引擎适配与资源检查](engine-profiles.md) |
| Diversion、Git、Perforce 等怎样保存版本和协作     | [版本控制与协作适配](version-control.md) |
| 第三方包、变更、导出、备份怎样处理                | 本文第 6–9 章                            |
| 如何逐步采用、复制项目约定、检查合规              | 本文第 10–11 章                          |
| 两份参考具体吸收了什么、哪些规则有调整            | [来源对照与设计取舍](guide-sources.md)   |

新项目先确定四件事：项目短名、引擎工程位置、自有内容根目录、制作源文件位置。采用标准方案表示采用本文的文件组织规则与命名规则，并选择对应引擎适配；版本控制沿用已有方案，无方案时先记录可恢复的保存方式，不自动建立仓库。技术检查只应用于实际拥有的资源类型。用户无需提前建立全部示例目录、填写所有类型参数或阅读所有参考章节。

## 1. 适用范围与优先级

**G01 必须：** 先尊重引擎必需结构、语言约定与现有项目规则。实际优先级为：工具的硬性要求 → 项目明确记录的选择与例外 → 本规范默认值。新成员和 Codex 使用同一份项目约定。

**G02 必须：** 在 `PROJECT_STRUCTURE.md` 或现有等价文档记录采用版本、章节和引擎适配。只采用命名章节时，不因此强制引入交付流程或重建目录。例外写清适用位置、原因和验证办法；无需设立审批角色。

**G03 应当：** 文件类别不存在时不创建空目录；已有一致且有效的组织方式可作为项目例外保留。原 1.0“轻量方案”和 1.1 采用者保留原选择，升级指南不会自动扩展范围或改用其他版本控制后端。

本文的“必须”约束已采用章节中适用的规则；“应当”是默认做法，可记录原因调整；“可以”是按需选项。规则编号用于在建议和检查结果中精确引用。

## 2. 四个容易混淆的概念

| 概念           | 例子                         | 记录方式                                            |
| -------------- | ---------------------------- | --------------------------------------------------- |
| 资产身份       | 巡林者这一个角色             | 稳定资产名 `ranger`；工作台内使用已有资产 ID        |
| 外观变体       | 冬装、夏装                   | `ranger_winter`、`ranger_summer`                    |
| 修订版本       | 冬装修改了第三次             | 仓库固定修订、工作台版本或交付目录 `v003/`          |
| 文件用途与格式 | 模型、基础色、预览；GLB、FBX | `ranger_winter.glb`、`ranger_winter_base_color.png` |

**G04 必须：** 变体编号、动画帧号、LOD 与修订版本分别表达。`rock_03_lod1` 表示第 3 种岩石的 LOD 1，不表示第三版模型。参考图、概念图和最终模型可关联同一个角色，但各自仍是不同制作产物。

## 3. 项目外层：每一份文件有明确职责

```text
forest_relics/
├── PROJECT_STRUCTURE.md
├── game/                    # 引擎工程，内部遵循所选适配
├── art_source/              # 已确认定稿的可编辑源文件，按内容语义组织
│   └── characters/ranger/ranger.blend
├── docs/                    # 设计、技术约定、来源清单
│   └── references/          # 制作参考，不作为运行资源
├── tools/                   # 导出与转换工具，有需要时创建
├── deliveries/              # 对外交付快照，或使用独立交付存储
├── scratch/                 # 本地实验与制作中未确认的过程稿；不纳入版本控制
│   └── work/                # 正在制作、调参或待审的半成品／准备稿／候选稿
└── .game-studio/             # 由插件管理，登记后才出现
```

**D01 必须：** 区分引擎工程、制作源文件、参考资料、工具和可再生输出。已有引擎工程在根目录时继续使用 `./`，不强制搬进 `game/`。`docs/` 中的设计说明和参考不能被打包规则无意纳入游戏。

**D02 必须：** 每种已确认定稿（或已正式接入引擎）的可编辑内容有明确的权威源文件，位于 `art_source/`。源文件与导出物用共同词根关联，例如 `art_source/characters/ranger/ranger.blend` 导出到引擎角色目录。制作过程中的半成品、自动绑定准备稿、未获用户确认的候选稿及返修试做稿一律放在 `scratch/work/`（或由工作台在 `.game-studio/` 内管理），严禁提前放入 `art_source/`，也严禁在 `art_source/` 下嵌套建立阶段或版本子目录。可以使用引擎直接导入源文件的流程，但必须说明编辑位置、所需工具及版本；不要维护两份各自变化的“主源文件”。

**D03 应当：** 源文件和引擎内容之间保持可理解的对应关系，不要求逐层镜像。已定稿的源工程内部可包含高模、烘焙工程、分层绘画等未单独交付的制作层，但尚未定稿的独立过程文件须留在 `scratch/work/`。预览图标明预览用途；不能把预览图片作为同一资产的新模型版本。

**D04 必须：** 自动生成与手工编辑内容应能区分。工具输出记录生成方式；需要手工修改的结果另存为新的权威输入，避免下一次转换覆盖工作。临时缓存可以重建，源文件与配置不能按缓存清理。

## 4. 引擎内层：内容就近，公共部分有边界

以下是逻辑目录示例，`<content_root>` 在 Godot 可以是 `res://forest_relics/`，在 Unity 可以是 `Assets/ForestRelics/`，在 Unreal 可以是 `Content/ForestRelics/`。例子用通用小写形式；引擎适配允许改变大小写。

```text
<content_root>/
├── core/                    # 基础契约、启动机制、可复用基类
│   ├── bootstrap/
│   └── interaction/
├── systems/                 # 游戏级系统的具体实现
│   ├── save/
│   └── quests/
├── characters/
│   ├── ranger/              # 模型、材质、动画、场景／预制体、专用逻辑
│   └── shared/              # 仅角色领域共享，例如同骨架动画
├── props/wooden_chest/
├── environments/forest/     # 场景用素材与组件，不是关卡入口
├── effects/fireball/        # 特效及专用纹理、材质、逻辑
├── ui/inventory/            # 界面组件与专用资源
├── audio/music/             # 项目范围的音乐、环境声等
├── levels/                  # maps 可作为项目选定的等价名称
│   ├── campaign/forest_entrance/
│   ├── overview/            # 需要展示资源集时创建
│   └── demos/               # 需要演示使用方式时创建
└── shared/                  # 真正跨领域复用的资源
    ├── fonts/
    └── material_library/
        ├── surfaces/
        └── utility/
```

**D05 必须：** 新的自有内容归入明确的项目或包命名空间。根目录不得持续堆放无归属的素材。第三方包、自有插件和 DLC 各有可识别边界；引擎要求的根目录与已有工程结构是记录在案的例外。命名空间降低冲突概率，但迁移仍需检查依赖。

**D06 应当：** 先按内容／功能，再按资产或子功能组织。专用资源与使用它的场景、预制体或功能放在一起。少量文件直接平放；大型动画集、音频集可按 `locomotion/`、`combat/`、`dialogue/` 等用途细分。单个大型资产内也可按需增加 `textures/`、`animations/`。不要在全项目先分 `textures/`、`models/`、`scripts/`，导致查一个角色需要横跨多个大目录。

**D07 必须：** 实验区有明确边界。纯工具实验放外层 `scratch/`；需引擎编辑或运行的实验放引擎允许的位置，如 `res://sandbox/`、`Assets/Experiments/` 或 UE 的 Developers 区。正式内容不得引用实验资源。实验晋升时连同依赖检查、源文件关联、命名和引用一起处理，不只改变路径。移入正式目录本身不代表通过引擎验收。

**D08 必须：** 区分实验的受管范围、本地取得范围、引擎导入和发行打包四个设置。本地实验可按所选后端排除；需要协作的实验可进入分支或受管目录，并明确发行排除规则。不能用仓库忽略规则代替打包排除，也不能排除导入后仍期待游戏加载它。采用选择性同步／稀疏工作区时，不能将未下载资源误报为仓库丢失。

**D09 应当：** 不建立空目录占位或 `misc/`、`new_folder/` 等长期收纳箱。未分类的外来资源可进入明确的暂存区，记录用途后再晋升。清理目录前检查隐藏文件、身份元数据和引用；使用引擎支持的方式处理遗留引用，不能因为编辑器显示为空就直接删除磁盘内容。

### 4.1 core、systems、shared 的区别

| 位置                 | 放什么                                     | 不应放什么                         |
| -------------------- | ------------------------------------------ | ---------------------------------- |
| `core/`              | 交互接口、基础角色契约、启动协调等底层机制 | 某个关卡、武器外观、临时调参资源   |
| `systems/`           | 存档、任务、背包规则等完整游戏系统         | 所有无法分类的脚本                 |
| `characters/shared/` | 多个兼容角色共同使用的动画或资源           | 只被巡林者使用的资源               |
| `shared/`            | 跨领域复用的字体、通用材质等               | 为“将来可能复用”提前搬来的所有资源 |

**D10 必须：** 基础机制与具体配置分开。例如交互契约在 `core/interaction/`，木箱开箱表现和配置在 `props/wooden_chest/`。调具体内容时优先修改配置、实例或派生实现；改变公共基类时检查已有使用者。

**D11 应当：** 在实际复用发生时提升共享范围。两名角色共用的动画先进入 `characters/shared/`，只有跨角色、场景等领域共用时才进入项目级 `shared/`。不要依赖目录名推断骨架或格式兼容性。

### 4.2 材质库与调试资源

**D12 应当：** 通用材质、可复用 shader／材质函数、平铺纹理和噪声放在 `shared/material_library/`，角色专用材质留在角色旁。采用母材质体系时，共享母材质在材质库，具体实例在使用方；其他引擎可用等价的 shader 加材质配置表达。

**D13 必须：** 调试材质、碰撞可视化和测试纹理有明确标识和发行策略。可以位于材质库内的 `debug/`，但正式内容不能遗留对将被剔除资源的引用；保留在开发构建中的依赖也必须在发行构建验证。不要假设名为 `debug` 的目录会被自动排除。

### 4.3 关卡、组件场景与演示

**D14 必须：** 可游玩关卡与主入口集中在选定的 `levels/` 或 `maps/` 下，并记录实际构建入口。Godot 的角色场景和 Unity 的角色预制体仍属于角色，不能把所有 `.tscn` 或 `.prefab` 都移入关卡目录。

**D15 应当：** 大关卡按职责拆分时，在同一关卡目录表达 `geometry`、`lighting`、`audio`、`gameplay` 等层的用途，记录组装入口。资源包按需要提供 overview 场景展示内容，提供 demo 场景解释使用；两者可以合并。它们是否进入正式游戏包需要显式决定。

## 5. 依赖、复用与迁移边界

**R01 必须：** 使用引擎资源引用、项目相对路径或明确的包接口。禁止正式内容依赖作者电脑的下载目录、个人绝对路径或未交付的外部文件。外部纹理、材质、字体、动画骨架也是依赖，不能只检查主模型。

**R02 应当：** 默认依赖方向为“关卡组装具体内容；具体内容使用系统接口、core 和共享资源”。`core` 不硬引用具体角色或关卡；启动时通过配置或组装层注入选择。`shared` 不反向引用内容模块的私有文件。循环依赖需要重构边界或记录其必要性，不能靠相互复制解决。

**R03 必须：** 跨项目复用时检查完整依赖闭包。迁移木箱时，检查箱子材质、母材质、纹理、shader 与插件，而不只复制模型。目标项目有同名资源时先比较来源、内容和接口；禁止默认为同一资源并覆盖。例如两个项目各自修改的 `master_surface` 必须保留各自命名空间或显式合并。

**R04 应当：** 基础游戏可以被 DLC 引用，基础游戏不应硬依赖可卸载 DLC。DLC／内容包独立命名空间，声明所需基础版本；验证移除可选包时主游戏仍能运行。第三方包的依赖与项目私有依赖同样需要登记。

## 6. 文件命名与类型约定

默认采用 `asset_name[_variant][_purpose][_detail].extension`，字段含义、类型词典、完整资源组和正反例见[命名与资源类型速查](asset-naming.md)。采用标准方案时该文件的适用命名规则一并生效。

同一资产使用共同词根；类型、变体和用途各有位置。通用资源默认 snake_case；原生前缀和语言类名遵循选定适配。显示名称、文档和标签可使用中文。命名字段用于人读和搜索，不应替代元数据成为脆弱的业务解析协议。

## 7. 第三方内容与资源入库

**P01 必须：** 登记包名、来源、版本、许可文件位置和本地修改。第三方包按引擎或包管理器要求安装；导入前检查其根目录、公共依赖与自动执行内容，不凭“来自商店”假定它遵守当前规范。保留作者声明，未经检查不批量改写包内部路径。

**P02 应当：** 第三方原包与项目自己的封装可区分。通过项目侧材质配置、派生场景或适配脚本定制时记录原包版本；必须直接修改包时记录补丁，以便升级比较。无必要不要复制一个公共库到每个资产文件夹。

**P03 必须：** 资源进入正式运行目录或 `art_source/` 定稿源目录前检查五项：归属与名字、完整文件集、可编辑来源、引用完整性、目标工具实际加载，且须经用户明确确认定稿（或明确授权正式接入）。采用技术检查章节时，再执行相应类型检查。下载成功、生成完成、工作台预览成功或局部预检／返修各自只证明对应步骤，不得据此将未定稿过程产物提前写入 `art_source/` 或正式运行目录。

**P04 应当：** 一个 `docs/asset_sources.md` 就可以管理小项目来源，按资产组或第三方包记录即可。AI 生成资产在信息可得时记录工具／模型、参考输入、任务和人工修改；未知项写未知，不补造来源。参考图与用于游戏的可交付文件标明各自用途。

## 8. 工作修订、发布与交付

**V01 必须：** `art_source/` 与正式运行目录只保留当前唯一有效定稿，日常编辑保持稳定文件名。修订由所选版本控制后端、工作台版本或明确的快照记录管理；外观变体不能充当修订。需要复现时记录后端、仓库／存储和固定修订，不只写分支或工作区名。未获用户确认的过程稿、准备稿与中间废稿严禁加入项目版本控制（Git / LFS / DVC）或正式来源／部署清单，也不强制归档，允许用户在 `scratch/` 中直接覆盖或随时删除旧过程稿而不触发任何校验报错。正式引用不得随意指向 `latest` 或 `final_final`。

**V02 必须：** 已对外交付的版本保留原内容，新交付产生新版本目录或等价存储版本。最小交付包示例：

```text
deliveries/forest_props/v003/
├── README.md               # 入口、目标引擎、导入方法、限制与验证结果
├── manifest.json           # 或其他等价清单；不要求特定 schema
├── assets/                 # 完整运行文件集
├── previews/               # 预览与实际资产明确区分
└── licenses/               # 适用的来源与许可记录
```

**V03 必须：** 清单至少记录包版本、主文件、依赖、源文件位置和实际验证范围。需要可复现导出时增加源版本、校验值、工具版本与参数。相同 `.glb` 扩展名不能证明两份导出在材质、动画或扩展兼容性上相同。

**V04 应当：** 分开记录格式检查、引擎加载、运行表现和美术审核。未检查标明“未验证”；有意保留的警告记录原因。overview 和 demo 用于帮助接收者理解资产，不能替代目标引擎验收。

## 9. 版本控制、生成文件与工作台数据

**S01 必须：** 源码、已定稿的制作源文件（`art_source/`）、必要工程配置与资源身份信息有可恢复副本。引擎元数据不能一律视为缓存。生成缓存、日志、本地构建产物与制作中的未确认过程稿（`scratch/`）按实际引擎与工程规则排除在版本控制和正式清单之外；先确认可重建或属未定稿过程产物，再制定清理规则。

**S02 应当：** 多人编辑难以合并的二进制文件时明确编辑归属与锁的实际语义。大文件采用后端原生支持、扩展或专用存储，由实际方案决定；Git LFS 只是 Git 适配的一种选择，不要求其他后端使用它。换行、忽略、下载范围与大文件规则记录在项目配置中，不修改用户全局配置来迁就某个项目。

**S03 必须：** `.game-studio/` 保存真实数据库、不可变资产版本、制作与交付记录，不是临时缓存。它由插件管理，不能手工整理资产路径或覆写受管文件。按需通过工作台改显示名或创建新版本；本规范不更改插件支持的导入格式。

**S04 必须：** 工作台数据的仓库受管范围、云同步和一致性备份分别决定。当前插件不提供自动数据库备份或 VCS 数据库协作；不能合并多份活动数据库，也不能把它们自动同步后称为一致性备份。明确活动数据库的同步排除和可恢复快照，资产文件也需有保存方案。若引擎根目录包含它，按引擎方式排除导入与打包。已有工作台导出可直接作为交付记录，不必重复复制。

具体要求与后端映射见[版本控制与协作适配](version-control.md)。通用规则关注固定版本、完整变更、冲突策略、取得依赖和恢复；提交、同步、共享分支集成、发布与备份分别记录。选择后端不自动触发迁移或启用远端功能。

## 10. 项目约定模板与渐进采用

复制后只填写已经作出的选择。2D 项目没有骨架或 PBR 贴图时，不需要填写对应参数；不存在的入口、工具和备份不得写成已完成。

```markdown
# 项目文件约定

- 规范版本：Open Game Studio 1.2。
- 采用范围：标准方案；技术检查仅适用实际资源类型。或列明选用章节。
- 项目短名／显示名：forest_relics／林谷遗迹。
- 引擎与版本：填写实际版本；工程位置 game/ 或 ./。
- 内容根目录：填写真实位置；关卡入口及启动方法：填写实际入口。
- 源文件位置：art_source/；直接导入源文件的例外：按实际情况填写。
- 命名适配：通用 snake_case；语言类名／UE 前缀等例外列明。
- 类型词汇：采用命名速查默认值；别名、语音语言码等项目选择列明。
- 内容边界：core、领域共享、全局 shared 的实际位置。
- 第三方包与来源记录：填写位置、包安装约定。
- 实验区：填写位置、是否追踪、是否导入、是否参与发行。
- 模型约定（适用时）：单位、轴向、枢轴、模块网格、骨架。
- 贴图约定（适用时）：色彩空间、normal 方向、打包通道、用途预算。
- 版本控制：已有后端、仓库／存储、工作区及代码／美术的权威范围；未选择时写明。
- 同步／锁：是否自动云同步、更新与下载范围；锁限制编辑还是提交，实际可用性。
- 版本／交付：填写固定修订记录方式、输出位置与实际验收步骤。
- 保存与备份：填写源码、源文件及工作台数据的实际恢复方式。
- 迁移范围：默认新增文件；已经授权的旧文件迁移另列清单。
- 例外：规则编号、适用位置、原因、验证方法。
```

**A01 必须：** 先读取既有约定和实际目录，再生成项目选择。新建项目只创建当前有用途的目录；已有项目默认从新增文件开始采用。调整或停止采用只更新项目约定，不影响插件功能。

**A02 必须：** 用户请求执行旧文件迁移时，先准备路径映射和引用影响，再按授权范围迁移。映射包含旧路径、新路径、身份元数据、引用方、第三方归属与恢复方法；缺少引擎工具时不要把普通磁盘搬动当作引用已修复。迁移后检查加载、导入设置、入口运行和构建范围。

## 11. 自查与结果表达

这些规则当前通过人工或 Codex 按实际工具检查，不代表插件已内置自动执行器。问题报告至少包含“规则编号、文件位置、观察到的问题、建议、是否已验证”；不能仅因不同于默认模板就报错，应先读取采用范围和例外。

| 检查时点     | 检查什么                                       | 发现问题时                           |
| ------------ | ---------------------------------------------- | ------------------------------------ |
| 新建／导入   | N01–N07 命名、D01–D06 位置、P01–P04 来源与依赖 | 改名建议或入库问题清单               |
| 晋升正式资源 | D07–D15 边界、R01–R04 依赖、适用 Q 规则        | 缺文件／错误引用需修复；美术问题单列 |
| 重命名／移动 | A02 身份、引用、导入设置、实际加载             | 保留恢复途径，验证受影响范围         |
| 交付         | V01–V04 版本、完整清单、目标工具与发行排除     | 未验收项标明范围，不宣称兼容         |

建议严重度：违反已采用的“必须”规则或导致引用失效为错误；偏离“应当”且无解释为建议；不适用或已有合理例外的不报违规。文件组织合规、技术正确与视觉质量分别记录。
