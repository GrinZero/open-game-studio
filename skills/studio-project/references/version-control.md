# 版本控制与协作适配

[返回规范](project-file-guide.md) · 版本 1.2 · 参考日期：2026-10-13

文件组织规范独立于版本控制工具和引擎。用户可以选择 Git、Diversion、Perforce、Unity Version Control（原 Plastic SCM）或其他有恢复能力的方案；采用命名与目录规则不要求安装 Git。已有项目继续使用既有后端，只有明确选择更换时才制定迁移计划。

这里是项目约定与操作参考，Open Game Studio 当前没有这些服务的仓库管理、云同步或文件锁连接器。具体操作通过用户已配置的客户端或工具完成，不能把文档适配描述为插件已完成 API 集成。

## 1. 通用要求：先约定能力，再选择实现

**C01 必须：** 记录每类文件由哪个系统负责版本与保存：代码、已定稿的制作源文件（`art_source/`）、运行资产、工程配置、交付包、工作台数据。可以使用一个仓库，也可分开存放，但每一类只能有明确的权威位置和可恢复方法。未获用户确认的制作过程稿、绑定准备稿与候选实验（位于 `scratch/work/` 等临时区）严禁纳入仓库版本控制、大文件存储（LFS / DVC）或受管来源／部署清单，防止版本库因过程迭代膨胀，并保证本地过程稿可随时直接删除。引擎选择不决定后端：Godot 可以用 Diversion，Unreal 可以用 Git，Unity 可以用 Perforce。

**C02 必须：** 需要复现的制作或交付记录固定版本身份：后端、仓库／存储标识、精确修订标识、路径或依赖清单。分支名、工作区名和 `latest` 会变化，不能单独作为交付依据。标签／label 可方便浏览，但交付仍记录其当时指向的固定修订或完整文件清单。

**C03 必须：** 提交一个能理解和恢复的变更单元。一起修改的模型、材质、纹理、身份文件和引用更新应一起提交；不把“移动文件”“丢失元数据”“修引用”拆成会使共享版本无法加载的中间状态。内容增量与大型批量重命名尽量分开，说明写清做了什么、为什么和如何验证。

**C04 必须：** 区分本地保存、工作区同步、仓库提交、共享分支集成、交付发布和备份。不同系统可能合并部分操作，但不能因此混淆结果。例如未提交文件已经同步到云工作区，仍不等于它有可复现的仓库提交或已经发布。

**C05 必须（多人编辑难合并资产）：** 明确编辑归属和冲突处理方法。选择编辑预约、软锁提醒、硬锁或独占 checkout 时，记录实际限制的是本地编辑、提交还是推送，以及跨分支作用域。没有硬锁也可通过约定避免并行编辑；不能把“有提醒”当作“别人无法修改”。独立开发者无需建立不存在的团队流程。

**C06 必须：** 分开配置四件事：哪些文件进入仓库、当前工作区下载哪些文件、引擎导入哪些文件、发行包包含哪些文件。忽略规则、选择性同步／稀疏检出、引擎排除和打包设置互不替代。制作中的半成品在未获用户确认定稿前保持在版本控制忽略区（如 `scratch/`），不得为临时过程稿逐版写入正式忽略白名单或大文件追踪描述。规则改动后检查实际结果；已经受管的文件不能仅添加忽略条目就假定从历史消失。

**C07 应当：** 按文件实际合并能力选择策略。代码和部分文本配置可比较合并；文本形式的场景也需保留结构与身份关系，必要时使用引擎合并工具。Blend、PSD、蒙皮模型和二进制场景等难合并对象，冲突时保留双方版本、确定基准并人工整合，不宣称 VCS 能自动合并美术内容。

**C08 必须：** 恢复旧版本前确认修订、目标路径和当前未提交工作；使用该后端支持的恢复／搁置方法保留需要继续的修改。恢复后检查资产与引擎状态，并产生可追溯的新变更。只采用规范不会触发清理、历史改写、强制解锁或仓库迁移。

**C09 必须（混合存储）：** 分开管理代码和美术时，发布清单必须同时固定各自修订。不能用“代码分支 main＋美术最新”描述一个版本。源文件和运行导出分属两个系统时，保存源修订、导出设置和产物清单的对应关系；同一文件不要由两个自动同步系统同时写入。

**C10 应当：** 在新环境演练一次恢复：拿到已记录版本，取得必需依赖和大文件实体，打开目标入口。版本历史、云同步与可恢复备份分别检查；工作台受管数据库按一致性快照恢复，不通过合并两份活动数据库进行协作。

## 2. 常见后端映射

此表用于表达项目约定，不是性能排名；版本、托管环境、套餐和管理员配置会影响实际能力。无需为采用规范学习所有后端。

| 后端                       | 固定修订记录                                                     | 团队共享方式                                                              | 忽略／取得文件                                                     | 难合并资产的策略                                 |
| -------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------ |
| Git，按需搭配 LFS          | 仓库标识＋完整 commit ID；大文件实体与指针需一致                 | 普通远程流程区分 commit 与 push，集成目标分支后才成为该分支内容           | `.gitignore`；按项目配置取得大文件与稀疏范围                       | 明确归属；采用 LFS 锁时核实托管端与验证配置      |
| Diversion                  | repo 标识＋commit 标识；branch／workspace 为上下文               | 工作区可自动云同步，commit 才进入分支历史；同步与更新设置决定实际到达状态 | `.dvignore`，兼容的 `.gitignore` 规则；Selective Sync 决定本地目录 | 软锁提醒；具备相应能力时使用硬锁，核实实际配置   |
| Perforce P4                | server／depot／stream 上下文＋已提交 changelist 或固定文件修订集 | pending changelist／shelf 与已提交 changelist 分开                        | P4IGNORE 选定的忽略文件；client view 与同步范围决定本地文件        | 文件类型 `+l` 的独占打开，或提交锁；二者语义不同 |
| Unity Version Control      | 仓库标识＋changeset 标识；分支作为上下文                         | 按客户端工作区与 check-in／集成流程验证                                   | 使用该客户端的忽略和工作区配置                                     | 可按项目配置 Smart Locks，检查分支和版本规则     |
| 独立阶段快照／专用资产存储 | 固定快照或对象版本 ID＋完整清单／校验值                          | 按存储实际上传与交付流程                                                  | 显式选择快照范围和依赖                                             | 单人归属、独立候选副本；不能宣称具备分支合并     |

小型单人项目可以使用可恢复快照阶段性起步，并在项目约定中写清限制；命名和目录规则不因此失效。需要频繁协作或完整修订历史时再选择对应能力，不将网盘的“同步完成”直接称为版本控制完成。

## 3. Diversion 适配

### 3.1 仓库、分支、工作区分别记录

Diversion 将仓库、分支和工作区分开表达：工作区可同步个人未提交修改，commit 将选定修改加入分支历史。多设备或独立并行任务应使用各自的工作区，而不是让多台机器／多个任务共同写一个本地目录。交付至少记录 repo 和固定 commit；工作区名只是制作环境说明。[官方概念](https://docs.diversion.dev/concepts/repo-branch-workspace)、[提交说明](https://docs.diversion.dev/basic/what-to-do-with-your-changes)。

项目约定示例（占位内容需按实际项目填写，示例不代表插件持久化 schema）：

```text
版本控制：Diversion
仓库：填写实际 repo 标识或位置
共享分支：填写实际分支
当前工作区：填写自己的工作区
交付基准：填写已提交 commit 标识，不只记录分支名字
文件范围：代码、运行资源、制作源文件是否同仓库
忽略规则：仓库 .dvignore，以及存在时生效的 .gitignore
同步：当前是否暂停；是否自动更新共享分支
下载范围：必需目录和依赖，是否使用 Selective Sync
锁：软锁提醒；硬锁是否可用、哪些路径使用、何时释放
工作台数据：活动数据库的同步排除与一致性备份方式
```

### 3.2 同步、自动更新、commit 是不同状态

- **工作区同步**负责本地与云工作区之间的文件变化，可能包含未提交文件。暂停时不能把本地改动报告为已到达远端。
- **自动更新**控制共享分支的新提交是否进入工作区。关闭自动更新与暂停整个同步不同；新分支提交可能存在，而当前工作区仍基于旧状态。
- **Commit**将选定变更登记到分支历史。通常无需再执行 Git 式 push，但同步暂停、错误或连接问题仍需检查实际状态，不能看到本地保存或按钮操作就宣称团队已收到。
- 验收、复现和批量导出应固定明确的提交与依赖，并确认工作区没有混入新的自动更新或未提交资源；按已选流程使用独立工作区／分支或明确的更新策略。

这些区别来自[同步文档](https://docs.diversion.dev/concepts/syncing)。读取状态可使用官方客户端或 `dv status`；需等待同步时，先核实所用客户端的参数，不能让一个等待结果替代提交与引擎验收。[状态命令](https://docs.diversion.dev/cmd-ref/status)。

### 3.3 大文件无需套用 LFS 设置

Diversion 面向大二进制项目提供原生存储流程，本规范不要求它额外安装 Git LFS 或生成 `.gitattributes`。是否实际支持所需文件、仓库容量与操作范围，依据当前服务配置验证；原生大文件支持不能解决二进制内容的自动合并，也不证明离线和云端保存状态一致。[官方介绍](https://docs.diversion.dev/introduction)。

### 3.4 软锁与硬锁的实际边界

软锁展示其他工作区／分支中的编辑信号，不阻止他人编辑或提交。看到提醒后按项目约定联系编辑者或暂缓操作，不能只把图标当作已获得独占权。[软锁](https://docs.diversion.dev/soft-locks)。

硬锁限制其他用户对锁定路径的提交；其他人仍可能打开、编辑并本地保存。取得锁后确认所有者与路径，提交、集成或交接后按项目规则释放。不要把 Diversion 的硬锁写成“强制把本地文件设成只读”。当前官方文档将硬锁列为 Studio／Enterprise 能力；自动锁／释放还依赖仓库配置。规范不假定用户账户已经具备这些功能。[硬锁](https://docs.diversion.dev/hard-locks)。

### 3.5 忽略与选择性同步

`.dvignore` 决定受管范围，Selective Sync 决定当前工作区下载的目录；后者不会将对应内容从整个仓库删掉。官方文档还说明会识别现有 `.gitignore`，二者共存时需检查合并后的规则，匹配器版本也会影响具体行为。生成的引擎模板是起点，需核对源文件、身份信息、缓存和工作台活动数据库；不要直接拷贝 Git 清单后假设效果完全相同。[忽略文档](https://docs.diversion.dev/basic/dvignore)。

选择性同步会改变本地文件的可用性，取消已同步目录可移除本地副本。检查依赖与局部目录中的散落文件，不能只下载角色模型而漏掉共享材质／骨架；也不能将“未下载”诊断为“仓库资源丢失”。更改范围前保留未提交工作，遵循客户端条件与确认流程。[Selective Sync](https://docs.diversion.dev/advanced/selective-sync)。

## 4. 其他后端的适用细节

### 4.1 Git 与 LFS

Git 用 `.gitignore` 表达未追踪文件的排除，已追踪文件不会因此自动取消追踪。普通远程流程中，本地 commit、推送、目标分支集成分别记录。使用 LFS 时，验证指针对应的大文件可由交付者与接收者取得；“Git 文件齐全”不等于大文件实体齐全。[Git 忽略规则](https://git-scm.com/docs/gitignore)。

采用 LFS 文件锁需确认服务端支持、客户端与锁验证配置；不能只在文档写了“锁”就承诺阻止所有并行操作。[LFS 锁](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-lock.adoc)、[验证配置](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-config.adoc)。`.gitattributes` 是该适配的设置，不生成到采用其他后端的项目中。

### 4.2 Perforce P4

记录 server／depot／stream 与工作区映射，交付依据已提交 changelist 或完整固定文件修订集。pending changelist 和 shelf 是工作状态，不能写成已提交版本。需要完整工程基准时，按已提交变更同步完整内容；只有当前变更单的文件列表不构成全部项目文件。

`+l` 文件类型限制同时打开编辑；`p4 lock` 允许别人打开编辑，但限制提交。项目明确选用哪种机制和文件类型，不能将所有锁机制合写成“别人无法修改”。[独占打开与提交锁](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/P4Guide/resolve.lock.exclusive.html)。忽略文件由 P4IGNORE 配置决定，client view 和同步范围另行配置，避免套用 Git 文件名。[忽略设置](https://help.perforce.com/helix-core/quickstart/current/Content/quickstart/admin-create-ignore.html)。

### 4.3 Unity Version Control

选择仓库、分支、工作区和 changeset 的实际身份；不要因名称含 Unity 就把它限定为 Unity 工程。需要保护难合并文件时可评估 Smart Locks，并确认实际规则和更新后的文件版本。只记录了锁图标不代表跨分支的版本已集成。[官方概述](https://unity.com/features/version-control)、[Smart Locks](https://docs.unity.com/en-us/unity-version-control/smart-locks)。

## 5. 代码与美术采用不同后端

这是一种允许的配置，例如代码使用 Git、制作源文件使用 Diversion 或 Perforce。代价是一次发布可能需要两个修订身份和一致的依赖映射。先定义各自负责的路径和编辑者，不在同一活动目录上重复启用两个写入流程。

交付说明至少能回答：

| 内容               | 应记录的固定来源                       |
| ------------------ | -------------------------------------- |
| 游戏代码与导入配置 | 实际代码仓库和修订                     |
| 美术源文件         | 实际资产仓库、修订和源路径             |
| 引擎运行资产       | 导出来源、目标预设、存储修订或文件清单 |
| 使用的第三方包     | 包版本、来源与必要本地补丁             |
| 最终交付           | 清单、实际验证范围和取得全部依赖的方法 |

对于独立开发者，优先保持自己能理解和恢复的流程；只有清晰的文件职责或存储需求时才拆分系统。

## 6. 工作台与仓库各自负责什么

Open Game Studio 的资产版本固定导入文件集与制作引用；外部 VCS 负责工程范围的版本与协作；交付记录固定交接产物；备份保证这些数据可恢复。一个系统不能仅凭存在就取代其他范围的记录。

活动的 `.game-studio/studio.db` 及其写入相关文件不适合作为可合并团队状态，也不能因自动云同步就视为一致性备份。先定义活动数据库的同步排除、暂停写入／一致性快照、资产文件保存与恢复流程；不能简单忽略整个 `.game-studio/` 后声称全部版本仍可恢复。跨设备使用工作台项目需验证真实一致性流程，当前插件没有 VCS 数据库协作功能。

采用本文只记录方案，不自动初始化仓库、启用云同步、更换后端、迁移历史、创建付费功能或修改远端权限。用户已经明确要求的具体配置／迁移工作，按授权范围执行并验证。
